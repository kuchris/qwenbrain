# Changes, history and unknown answers

Protocol fixed before the GPU run. See `configs/temporal-memory.json` for the
complete event stream, explicit expected source ids and shared system prompt.

Eight fresh synthetic people have initial project names effective 2026-01-01,
received 2026-01-02. All eight change projects effective 2026-02-01, received
2026-02-02. On 2026-02-10 the first two current names are corrected, and the next
two January names are corrected retrospectively. Late January corrections must
not replace February's current state. Old rows remain in the append-only store.

Three frozen-model arms run after each stage: F without evidence, O with a gold
relevant source, R with SQLite retrieval. No adapter training or live promotion.
All receive the same instruction to answer personal questions only from memory,
say exactly UNKNOWN when unsupported, and answer arithmetic/general knowledge
normally. Every answer, including UNKNOWN, is generated by the model. All use
fresh context, the original measured generator, greedy decoding and 24 tokens.
This prompt differs from memory-v1, so raw scores are not a prompt-controlled
comparison against the earlier experiment or its LoRA arm.

## Retrieval semantics

Retrieval receives only the question and the current observation date. One
explicit ISO date in the question is the requested effective date; otherwise
use the current observation date. Invalid, multiple or future dates return no
evidence. Match exactly one known full person name, then select the latest
effective state available by the observation date. Same-effective-date claims
are superseded by their later recording date (id breaks ties deterministically).
This pilot assumes such claims are authoritative corrections, not unresolved
conflicting assertions from multiple sources. It supports only project-name
state and explicit dates, not unrestricted language understanding.

The append stage uses manually structured source metadata, not an LLM encoder.
Historical answers mean the corrected history according to information currently
available. The observation cutoff prevents later corrections appearing in earlier
stages. A separate-process replay of all retrieval queries against the final store
also verifies that future rows cannot leak into earlier observation cutoffs.

## Queries and scoring

Each stage has two current-project question forms per person. The last two stages
also ask each person's project on 2026-01-15. Each stage includes four unknown
people (including recombined known name components), two before-first-record
dates, two future dates, two unsupported favorite-color questions, two ambiguous
two-person queries and the four original unrelated controls. The R arm can
retrieve an irrelevant project claim for a favorite-color question; the model
must still abstain. O supplies no source for unsupported questions.

There are 32 queries initially and 40 at each later stage: 112 per arm. Report
known-answer accuracy separately from unknown-answer accuracy to avoid rewarding
an always-UNKNOWN model with a misleading overall score. Also report per-category
counts, exact answer plus EOS, false abstentions, selected-source accuracy and
raw evidence/outputs. Repeated stages and paraphrases are not independent facts.
Eight identities and a single deterministic run do not establish general ability.

## Verification

CPU tests cover effective versus observed time, late corrections, observation
cutoffs, future dates, missing/ambiguous names, invalid records and reopen
persistence. Hash the database around every evaluation and compare full frozen
base hashes around the run. Source/config and live-checkpoint hashes must remain
unchanged. A separate Python process reopens the final SQLite file and reproduces
every R retrieval, including queries from earlier stages. This verifies database
process persistence; model generation is not rerun in that child process.

Run `compare-temporal-memory.bat` or `.venv\Scripts\python.exe -X utf8 -m
qwenbrain.experiment_temporal_memory`. Outputs belong to a new local
`runs/temporal-memory-*/` directory. CPU checks use
`.venv\Scripts\python.exe -m unittest discover -s tests -v`.

## Bounded presentation follow-up, fixed after inspecting raw-v1

The completed raw-v1 run retrieved all 64 answerable sources correctly but often
produced false abstentions, and guessed on missing people/attributes. Raw source
sentences use `As of DATE`, whereas store semantics use persistent effective
states; this leaves an avoidable presentation ambiguity for the reader.

One development follow-up uses `--evidence-format explicit` with the same facts,
queries, model, scoring and store. Change only the preceding evidence message:
name it as the memory lookup result, explicitly mark empty results, and explain
that a selected project state persists until superseded and has already passed
date/correction filtering. Include the source id and effective/received dates;
state that project records do not establish other personal attributes. These
messages are constructed from retrieved evidence, never expected answers. All
arms still use model-generated UNKNOWN; there is no deterministic answer bypass.
F always receives the empty-result message, including on answerable questions.

This changes several aspects of the evidence presentation together and uses
already-inspected data. It can diagnose/improve this interface but is not an
independent confirmation or an isolated causal test of each prompt sentence.
Retain raw-v1 results regardless of the follow-up outcome. The default command
continues to run raw; pass `--evidence-format explicit` to repeat the follow-up.
